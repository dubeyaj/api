02 · Architecture

Server-side UX, shared I/O, Oracle

The visible UX layer is the AAI-hosted client screenset. It passes a large fixed-format communication area to server session controller HSLRSYSC. The controller manages session/database lifetime, validates security and screen access, then dynamically calls a transaction service selected in the screenset data block. UX transaction modules call reusable database component modules; shared COBOL copybooks describe row layouts and fields that correspond to Oracle tables.

UX screensetAAI client sends screen data, current screenset and a transaction-service name in a fixed-size comm area.LARS_UX/inc/*.CPB, screen and request copybooks
Session serverConnects Oracle on first request; authenticates; checks screen commands; routes a request to the chosen COBOL transaction; returns response data.LARS_UX/cobol/main/HSLRSYSC.CBL
SecurityLDAP/common security component determines roles, menus, screen permissions, and data-view keys; DB modules retrieve related privileges.HSSACSSC000.CBL and HSLRGBDB098/099 calls

Batch/reportSeparate COBOL batch jobs, SQR reports, and shell wrappers operate alongside the interactive UI.LARS_UX/cobol/batch, LARS_UX/sqr/src, LARS_UX/scripts
03 · Request lifecycle

From AAI event to Oracle-backed response

1 · AAIUser action populates the data block, process indicator and selected transaction service.
2 · SessionHSLRSYSC connects on first call; maintains session until LAST/RLBK.
3 · SecuritySign-on/role and screen commands are resolved; screen-specific data view is checked.
4 · DispatchController calls WHAT-SERVER-PROGRAM using comm area + LARS global vars.
5 · TransactionService routes on request process flag, operates on screen data.
6 · Data accessService invokes HSLRGBDB* DB modules; requests commit/cancel through shared DB state conventions.
7 · OracleDB module executes table/procedure logic with LARS_OWNER schema contracts.
8 · ReturnService writes response into data block; controller copies to response area and AAI callback.
Fixed-format boundary: AAI-COMM-AREA, REQUEST, and RESPONSE are each 32,760-character fields. HSLRSYSC copies the AAI payload into DATA-BLOCK and back; transaction modules commonly have an unload → route → load structure.

Controller sequence and transaction boundary

Sequence is grounded in HSLRSYSC.CBL: the non-first-request branch refreshes security, calls 6000-CANCEL-TXN for closed screens, dispatches only when WHAT-SERVER-PROGRAM is nonblank, copies data to response, then calls the AAI AIBSTS00 callback. The first request instead opens the log and connects before security. The diagram abstracts error branches and optional transaction tracing for legibility.

04 · Authorization path

Security is a server-side request gate

The session controller passes app ID, user ID, role ID, current screenset, saved role choices, and sign-on state to HSSACSSC000. The component distinguishes initial sign-on, subsequent role choice, screenset change, and AAI service cancellation. On successful resolution, the controller retains role/menu/screen privileges and converts returned data-view keys into “view all” or scoped representative/organization filters used by later requests.

Returned controlController useImplementation evidence

Authorization vs data filtering: screen/menu permission and data-view scope are separate controls. A transaction may be callable at the screen level but still receive a restricted rep/org scope; investigate both security result and SQL predicates when explaining missing rows.
04 · Representative UX path

Add/remove reporting affiliation

HSLRRPTS007 is a concrete, traceable example tying a user-visible screen action to LARS organization relationships. Its comments describe adding/removing reporting affiliations for a representative, and the makefile explicitly compiles this module.

06 · Persistence trace

08 · Schema keys

Keep both ID and sequence

The copybooks and live TEST dictionary agree on the dual-key design: person, organization, party, license, appointment, and process entities include an ID number plus a sequence number. Association joins must carry both parts wherever defined; an ID-only join can duplicate or misidentify historical versions.

10 · Build & runtime

Solaris-era toolchain assumptions

Top-level makefile intentionally rejects a single root build. lars.mk composes four application-level targets, but each target chooses a different SQR backend and external compiler/runtime libraries.

TargetSources / outputBuild dependencies evidenced
LARS_SHAREDShared COBOL subproject and common include contract.Micro Focus COBOL; shared include path used by UX, integration and conversion.
LARS_UXCOBOL main, interactive transaction services, batch jobs; Oracle SQR.Solaris-style paths, Server Express 5.1, Oracle 11g client/precompiler, AAI runtime, SQR 8.31.
LARS_INTIntegration COBOL and feeds.Additional integration-specific source and build settings.
LARS_CONVConversion COBOL, Sybase SQR and conversion database scripts.Sybase client/SQR selection differs from UX Oracle SQR.
Do not run root make LARS as a workstation check. The tracked makefile explicitly exits with “not possible” at this level. The declared compiler paths point to absent enterprise Solaris build infrastructure, so no local compile was attempted here.
